Performance

The layers are built to cost little and to cost nothing at rest. This page lists what they cost, the settings that change it, and how to measure it in your own app.

What a layer costs

The numbers below were measured with the gallery's --bench on an Apple M4 Max (Metal, Retina 2×). Each layer sits on a 340×190 card over a moving scene, so it redraws every frame. GPU times leave out the fixed cost of waiting for the GPU, which only the benchmark pays.

  • Idle: nothing. A layer that isn't moving requests no frames.
  • CPU (render thread): 2–50 µs per layer per frame; progressive blur costs the most. A few layers do per-frame work of their own before they draw: electric 0.06 ms, aurora 0.08 ms, ink's fluid 0.22 ms and the simulated fire 0.39 ms.
  • First frame of an effect: 2–10 ms, which includes compiling its shader (see Warm up the shaders). When the system's shader cache doesn't hold the effect's GPU pipeline, it takes 20–60 ms, at times up to about 200.

GPU time per frame on the card:

GPU time Layers
Under 0.1 ms Nearly half the layers, including glow, shimmer, outline, inner shadow, jelly, tilt and the voice orb.
0.1–0.2 ms Pulse, reveal and its melt, mesh gradient, aurora, starfield, CRT, chroma split, glitch, color filter, light leaks, water, old film, sparkles, trail and heat haze. Ambient glow, motion blur and pointer shadow cover 0.75–1 Mpx and still take 0.14–0.16 ms.
0.2–0.3 ms Glass, fire, fog, shockwave, voronoi, and ASCII, plus a blurred copy of what is behind.
0.3–0.45 ms Swirl, liquid metal, spoiler, topography (it takes the height three times a pixel for the slope), caustics and bokeh.
Over 0.5 ms Rain on glass 0.51 ms; frost 0.62 ms; progressive blur 1.0 ms, the most, for its five copies of what is behind.

Progressive blur and frost don't animate, so they only redraw when what is behind them changes.

A few layers are drawn as Skia shapes instead of a shader, so their cost is on the CPU, with almost no GPU time. That time swings up to four times from run to run: fireworks 0.04–0.18 ms, confetti 0.1–0.5 ms, the particle network 0.09–0.32 ms, shatter's shards 0.1–0.4 ms while they fly, and shatter's dust 0.13–0.6 ms while it blows.

Slower GPUs scale these numbers up, but the ranking holds.

Cost grows with the area

A layer's GPU cost grows with the area it shades. A 700×500 panel of swirl takes about 0.77 ms per frame.

Layers only shade where they can draw. Flames and heat haze cover the area above the shape, not around it; a shockwave covers only its live rings; layers that only draw around the pointer repaint only around it; and the border-only layers (the border beam and the electric border) skip the interior. Layers that read the backdrop copy only the margin they sample.

Render scale

RenderScale shades a layer at a fraction of the display's resolution and scales the result up. At 0.5 it shades a quarter of the pixels:

<fx:Swirl Preset="Marble" RenderScale="0.5" />

On a 700×500 panel, RenderScale="0.5" takes:

Layer Full resolution RenderScale="0.5"
Swirl 0.77 ms 0.56 ms
Liquid metal 0.73 ms 0.47 ms
Voronoi 0.76 ms 0.40 ms
Aurora 0.62 ms 0.28 ms

Use it for large, soft, heavy layers, such as a window-sized aurora or swirl. Edges and grain soften. On cheap layers it costs more than it saves, because the scale-up pass takes about 0.1 ms: grain went from about 0.07 ms to 0.10–0.19 ms. Layers drawn as shapes (confetti, fireworks, shatter, particle network) don't use it.

Warm up the shaders

The first frame of an effect waits for its shader to compile. FXSettings.WarmUpAsync compiles every shader up front, in about 60 ms on the machine above. Start it early, for example when the app starts:

public override void OnFrameworkInitializationCompleted()
{
    // Set up the main window or view here.

    _ = FXSettings.WarmUpAsync();
    base.OnFrameworkInitializationCompleted();
}

On the desktop the shaders compile in parallel on the thread pool, off the UI and render threads. In the browser there is one thread, so they compile one at a time, and the task yields to the browser between them so input and rendering go on; each compile still holds the UI thread for its own few milliseconds. The warm-up compiles the shaders but not the GPU pipelines, which are built on each effect's first draw. The system caches those from one launch to the next. On the first launch on a machine, or once the system has dropped them from its cache, an effect's first frame takes 20–60 ms, at times up to about 200.

Content masks

Layers that follow the content's own pixels capture the child on the UI thread when it changes, not per frame. The distance field that Outline and InnerShadow need costs a few milliseconds per capture on the desktop. Content masks has the numbers.

In the browser

The browser runs .NET on one thread, so the app, the compositor and the effects share it, and the GPU work goes through WebGL. The shaders run as fast as on the desktop. What costs more is .NET code, which the browser interprets unless the app is compiled ahead of time (RunAOTCompilation).

Measured with ?bench on published builds, in Chrome on the Apple M4 Max at 60 Hz:

Interpreted Compiled ahead of time
As it is All 70 at 59–60 fps All 70 at 59–60 fps
CPU 4× slower (a mid-range laptop) All 70 at 58–60 fps; the simulated fire 44 All 70 at 57–60 fps
Download (Brotli) 5.9 MB 9.4 MB

In Safari 27 on the same machine (interpreted; Safari can't slow the CPU down), 64 of the 66 ran at 59–60 fps in a full run; the other two, shatter's shards (56) and fireworks (52), hold 60 when timed on their own. Safari compiles all the shaders in 67 ms. The effects added since (the color filter, dot grid, outline, inner shadow, beam, the five newer reveals, ink, silk and beams) all hold 60 fps there too, with 0.03–0.28 ms of .NET work a frame.

The layers that do their work in .NET code are the ones that slow down:

Layer Interpreted Compiled ahead of time
Shatter's dust 0.9–1.1 ms a frame 0.25–0.5 ms
Electric's bolts 0.45–0.6 ms 0.12–0.3 ms
Simulated fire 0.4–0.45 ms, plus 1.4–1.5 ms for its simulation steps 0.18–0.4 ms, plus 0.35–0.8 ms

Compiled ahead of time, these timings swing about two times from run to run.

If your app leans on the simulated fire, shatter's dust or electric and has to run well on slower machines, compile it ahead of time. Otherwise the interpreted build is enough. The browser gallery compiles ahead of time on a Release publish, with these properties in its project:

<PropertyGroup>
    <RunAOTCompilation Condition="'$(Configuration)' == 'Release'">true</RunAOTCompilation>
    <WasmDebugLevel Condition="'$(Configuration)' == 'Release'">0</WasmDebugLevel>
</PropertyGroup>

WasmDebugLevel 0 turns off debugger support in Release. With debugger support on, the runtime also stops optimizing interpreted code: shatter's dust took 6.6 ms a frame and ran at 22 fps even on the M4 Max.

WebGL can't make Skia wait for the GPU, so there is no GPU time in the browser: the frame rate is the measure.

Measure in your own app

FXDiagnostics times draws per layer type in your own app. It is off by default and free while off. Turn on IsEnabled, and MeasureGpu for GPU times, then read Collect():

FXDiagnostics.IsEnabled = true;
FXDiagnostics.MeasureGpu = true; // waits for the GPU on every draw: for measuring only

// Later, after the screen you want to measure has run for a few seconds:
foreach (var stats in FXDiagnostics.Collect())
{
    Console.WriteLine(
        $"{stats.Layer}: {stats.Draws} draws, {stats.CpuMsPerDraw:0.000} ms CPU, " +
        $"{stats.GpuMsPerDraw:0.000} ms GPU, {stats.MegapixelsPerDraw:0.00} Mpx a draw");
}

MeasureGpu makes every draw wait for the GPU, which slows frames down: use it to compare layers, not in a shipping app. FXDiagnostics.Backend tells you which GPU backend the measured draws ran on.

The gallery's bench

The desktop gallery times every layer in a real window on the GPU the app uses:

dotnet run -c Release --project samples/Nova.Avalonia.FX.Gallery.Desktop -- --bench bench.csv

Add --target 6 for the full-stage panel, --set RenderScale=0.5, --only fire,swirl (or a style, --only shatter:Dust), --full-quads to measure without trimming, or --cold to skip the warm-up. Besides every layer, a full run times shatter's dust, reveal's melt and the simulated fire on their own.

bench/baseline.csv is a full run on the machine above. To see whether a change made anything slower, run the bench again on the same machine and compare:

dotnet run -c Release --project samples/Nova.Avalonia.FX.Gallery.Desktop -- --bench bench/run.csv --compare bench/baseline.csv

It lists the layers that got slower or faster by more than run-to-run noise (25% and 0.04 ms on the GPU, 50% and 0.02 ms on the CPU), and exits with 1 when any got slower. A layer that looks slower is timed again first, up to twice, and keeps its best run: GPU clocks change with load, and the CPU time of the layers drawn as shapes swings up to four times from run to run. Timings only compare on the same machine and setup (the first line of the CSV records it). After a deliberate change, copy the new run over the baseline. Close other busy apps while it runs. First frames read 20–200 ms in a run where the system's shader cache didn't hold the layers' pipelines, and 2–10 ms in the run after; the compare leaves them out. The bench keeps its window on top while it runs and ignores the real pointer, which would take over from the scripted one. It exits with 2 when layers ran far under the frame rate of the others or drew nothing, as when the window was covered, on another desktop, or the display slept: their timings don't compare, so run it again.

Timing in the browser

?bench times every effect in the browser gallery (?bench=glow,fire:Simulated for some, &seconds=3 each): the frames painted a second, the 95th-percentile frame time and each draw's CPU time, printed in the console. A page in a hidden tab or window paints a frame a second or none, so scripts/browser-bench.mjs runs it in a headless Chrome, which also lets it slow the CPU down. It needs Node 22 or later and Chrome:

node scripts/browser-bench.mjs                    # against the gallery on http://localhost:5240
node scripts/browser-bench.mjs --cpu 4            # with the CPU 4 times slower
node scripts/browser-bench.mjs --url http://localhost:8080/ --only electric,shatter:Dust
node scripts/browser-bench.mjs --verify           # ?verify instead
node scripts/browser-bench.mjs --safari           # in Safari (a new tab; keep it in view)

Not measured yet: Firefox, phones, and slower GPUs.
